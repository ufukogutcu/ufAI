# ufAI platform guide

## Purpose and current availability

ufAI is a local-first application for one user to organize AI agents and related work across multiple workspaces in a browser. Its intended experience includes configurable agents, communication permissions, reusable skills, instructions, and triggers.

**Current availability: agents, asynchronous collaboration, host tools, terminals, attachments, and native media inputs.** Users can manage workspaces, create agents with saved characters on their flowboards, use a persistent Chat alongside separate task conversations, ask for live workload updates, and inspect learned memory. Agent Presets, saved Providers, model discovery/tests, Codex sign-in and usage, Ollama setup, themes, and automatic task-context compaction are available. Chat and ordinary tasks can read/write host files, run commands and interactive terminals, and publish downloadable files. Chat and task messages accept attached files. Supported models can inspect images and open PDFs through their native input capabilities. Agents can contact permitted collaborators and send deliberate messages to your workspace Inbox. Agents can also schedule one-time task check-ins. Agents can start work from saved schedules and custom events, including attached files. Audio/video perception remains unavailable. Reusable skills are available through each agent’s Skills tab, including custom packages and protected built-ins. The MCP tab connects agents to shared local or remote MCP servers for tools, resources and prompts. Interfaces and a dedicated built-in assistant remain planned. Settings contains controls for Inbox alerts.

One local installation holds one shared setup across browser sessions. There are no ufAI application accounts or separate profiles for each browser. Sign-in connects an external provider, runtime or MCP service account; it does not create a ufAI account. See the [terminology and feature-status guide](README.md) when explaining these distinctions.

## Available capabilities

### runtime-local

- **Status:** implemented
- **Purpose:** Use ufAI locally through a browser.
- **Behavior:** The local application must be running before the browser can open it. The usual address is <http://127.0.0.1:3000>, but an installation may use a different address.
- **Limitations:** The local process and machine must remain available. A page that cannot connect does not establish that saved data has been lost. Remote access and application-account sign-in are not provided.

### saved-data

- **Status:** implemented
- **Purpose:** Keep saved agents, task transcripts, memories, workspaces, Agent Presets, Providers, Vault secrets and user input requests, MCP servers and switches, custom themes, and application preferences on this local installation.
- **Behavior:** Saved records survive closing the browser and restarting ufAI. The selected workspace, active theme, and completed canvas pan/zoom positions are shared across browser sessions. Unsaved forms, open dialogs, and navigation history are temporary.
- **Limitations:** Saving and viewing data requires the local application to be reachable. There is no built-in full-installation backup, import, or export tool. Connection credentials and the rest of the saved installation data must be kept together when making a manual backup. Deleting saved records requires confirmation and has no in-app undo.

### dashboard-navigation

- **Status:** implemented
- **Purpose:** Reach Home, Vault, Agent Presets, Providers, Theme, and Settings.
- **Behavior:** Use the page icons on the left. Hover or keyboard focus shows their labels. Pages support direct links, refresh, and browser back/forward. The logo opens ufAI's [GitHub project](https://github.com/ufukogutcu/ufAI) in a new tab, keeping the current page and drafts open.
- **Dialogs:** Click or tap outside a dialog to dismiss it, following the same behavior as its Close control, including existing unsaved-change prompts. Only the top dialog closes when dialogs are stacked. Clicking inside or dragging from inside to outside keeps it open. Dialogs temporarily block dismissal while saving, deleting, or using a reset.
- **Appearance:** Backgrounds and panel surfaces stay steady. Switching workspaces or editors adds a tiny settling movement to foreground content. Dialogs, tooltips, small feedback messages, and individually created list items use brief entrance effects. Initial lists and additional result pages appear immediately. Motion follows the device's reduced-motion preference and does not delay interaction or dismissal.
- **Limitations:** Settings controls [Inbox alerts](#inbox-notifications). Use [Theme](#dashboard-themes) for appearance changes. If a preference cannot be saved, the last confirmed setting remains in use and Retry is available.

### shared-vault

- **Status:** implemented
- **Purpose:** Save encrypted secrets once and let all agents use them without requesting their values in ordinary chat.
- **Behavior:** Open Vault between Home and Providers. Search, create, rename, describe, replace, or delete secrets. Leave the replacement field blank to preserve its value. Saved values can be revealed or copied explicitly; reveal hides after 30 seconds or when the page loses focus. Deletion asks for confirmation. Secrets are shared across every workspace and agent, without destination restrictions or per-use approval.
- **Agent use:** Agents discover secret names and references, fill browser fields, or send authenticated API requests using those references. The normal tool outputs and history contain references and outcomes; known secret echoes are masked. Browser screenshots mask secret-filled fields and can be unavailable when those fields can no longer be located. HTTPS and local HTTP requests are supported; redirects require a separate request.
- **Storage and limits:** Unlocking is automatic on this computer. Keep the original connection credential key with the database when making a manual backup. Up to 256 secrets are supported, each containing 1–8,192 characters. Names and descriptions are visible metadata and should not contain secret values. Saved provider and MCP credentials remain in their existing editors.
- **Limitations:** This protects normal model context; it does not isolate unrestricted host commands from local keys or data. A receiving website or API receives the actual value and may transform or visually echo it beyond practical masking. There is no master-password lock, terminal injection, automatic credential migration, or key recovery. Deleting a secret does not revoke remote credentials or end existing website sessions.
- **Related references:** [Private input requests](#private-user-input), [Saved data](#saved-data), [Agent Browser](#agent-browser).

### private-user-input

- **Status:** implemented
- **Purpose:** Let agents ask for secret input privately while keeping the value out of conversation messages.
- **Behavior:** A request appears in its originating Chat or Task and in Workspace Inbox. Pending requests also appear in Vault and the agent’s input-count dialog. Choose **Open private request**, then enter a masked value, choose **Use a saved secret**, or select **Decline**. New values are saved in the shared Vault for all agents. The outcome and secret reference return to the agent. The agent can continue independent work and yield until an answer resumes its task.
- **Recovery:** Pending requests survive restarting ufAI. Repeated submissions do not create duplicate secrets. Conflicting replacements preserve the input and require explicitly choosing the latest saved revision before retrying. Cancelling or deleting the originating task closes pending requests; deleting an agent or workspace removes its requests while preserving shared Vault secrets.
- **Limitations:** Secret values use this private flow; ordinary questions use [user input requests](#user-input-requests). A task can have at most ten pending requests across all input types. Host access and receiving-site limitations are the same as for the shared Vault.
- **Related references:** [Shared Vault](#shared-vault), [Dashboard navigation](#dashboard-navigation).

### user-input-requests

- **Status:** implemented
- **Purpose:** Let agents collect information, clarification, choices and decisions in answerable cards while continuing independent work.
- **Behavior:** Requests appear in the originating Chat or Task and Workspace Inbox. Answer text and lists of up to four choices directly, including any Other option. Select **Answer** to open longer choice lists and forms. Forms group required and optional text, choice, Yes/No, number, email, URL, date and date-time fields. Check the displayed time zone when entering a time. **Send answer** submits all fields together. **Decline** tells the agent you are skipping the request. Use **View answer** to read an accepted answer in the conversation or Inbox.
- **Agent bubble:** A small input-count bubble beside an agent's warning/error bubbles shows its pending requests across Chat and Tasks, including while it works on something else. Click or activate it with the keyboard to open an answer dialog with task titles. The dialog stays open with No pending requests after its last request is answered.
- **Resumption and recovery:** Each answer or decline can resume the originating task automatically. Other requests stay open. Answers arriving during work are delivered when the task can handle them. Requests and accepted answers survive backend restarts. Failed or blocked tasks retain answers until repaired. Cancelling or deleting the source task closes its pending requests. Answering from another view replaces stale controls. Hiding fields and failed submissions preserve temporary drafts. Navigation prompts protect unsaved changes.
- **Privacy and limits:** Ordinary answers are saved locally and shared with the agent. Use the separate private card for secrets; only secret requests appear in Vault. A task supports ten pending requests, forms support twenty fields, and choices support fifty predefined options. Complete answers have an 8 KiB size limit. Agents are instructed to use cards whenever they need a user answer; this guidance does not guarantee model compliance. File uploads, nested/conditional forms, native Codex prompts and MCP elicitation are not part of these cards.
- **Related references:** [Private input requests](#private-user-input), [Workspace Inbox](#workspace-inbox), [Agent issues](#agent-issues).

### dashboard-feedback

- **Status:** implemented
- **Purpose:** Understand connection problems, failed actions and operations that are still running.
- **Behavior:** Background problems appear as compact notices at the bottom-right. When an agent panel or dialog is open, notices appear inside it so forms and the message composer remain usable. Each notice names the problem and offers a relevant retry when available. Repeated failures update the existing notice. View more notices expands the list when more than three are present.
- **Loading and recovery:** Spinners accompany active loading, saving and retrying. A sustained live-update interruption shows a connection notice while ufAI reconnects automatically. A brief restored message appears after a displayed interruption. Connection warnings do not mean that saved data has been lost.
- **Errors:** Form validation stays beside the affected field. Panel and dialog action failures remain near the action, and task/tool failures remain in their histories. Error notices stay until resolved or dismissed; optional Technical details provide additional request information. Dismissing a notice does not retry or fix the problem.
- **Limitations:** Notices are temporary and are not Inbox messages or a saved error history. Refreshing the browser clears their presentation state; unresolved problems may reappear when checked again. Reduced motion stops spinner rotation while retaining the loading text and icon.
- **Related references:** [Saved data](#saved-data), [Dashboard navigation](#dashboard-navigation).

### dashboard-themes

- **Status:** implemented
- **Purpose:** Choose Light Mode, Dark Mode, or custom application colors.
- **Steps:** Open Theme to see the gallery. Use a saved theme to apply it, or inspect a built-in theme to see its colors. Light Mode and Dark Mode are permanent and locked; choose Duplicate to customize a copy. Create theme can start from an existing theme.
- **Editing:** Give the theme a name, choose light/dark native controls, and search for a color or component. Groups contain color swatches, hex fields, and opacity sliders. The preview shows draft colors without changing the app. Selecting a preview swatch reveals its color control. The preview is collapsible on narrow screens. Back to library returns to the gallery; unfinished changes prompt before being discarded.
- **Saving and applying:** Save stores the theme. Use theme applies a saved theme. Saving changes to an already active theme updates the app's appearance. Cancel discards the draft; a failed save retains it. Deleting an active custom theme selects Light Mode.
- **Limitations:** The app initially uses Light Mode and remembers the saved choice independently of the device's appearance preference. There is no automatic system-following mode or theme import/export. Changes from another browser session appear on returning to the tab or reloading, without replacing unsaved drafts. Native browser dialogs follow the chosen light/dark mode rather than individually edited colors. After an application update, restarting ufAI may be necessary before saving newly available color options.

### dashboard-tooltips

- **Status:** implemented
- **Purpose:** Explain icons and other compact controls.
- **Behavior:** Hover or focus a control to see its label or help. Left page-menu labels appear after 100 ms of hover; other tooltips wait 400 ms. Keyboard focus shows tooltips immediately. Escape dismisses a tooltip; inside a dialog, the first Escape dismisses the tooltip before another Escape closes the dialog.
- **Limitations:** Disabled controls and touch hover do not show tooltips. Keyboard labels remain available independently.

### workspaces

- **Status:** partial
- **Purpose:** Organize related work into separate named spaces.
- **Steps:** On Home, use the plus button to create a workspace and its tab to select it. Create and Edit workspace accept a required name and an optional description of up to 4,000 characters. The selected workspace's description appears beneath its name when provided. Inbox, Triggers, Published Files, Edit workspace, Delete workspace, and Workspace actions sit beside the selected workspace’s name below the tabs. Right-click a workspace tab, or focus it and press Shift+F10 or the Menu key, to open Edit, Duplicate, and Delete actions for that workspace without switching to it. Workspace actions opens the same menu for the selected workspace. The create-workspace plus button remains beside the tabs.
- **Saving and switching:** Save stores both fields; Cancel discards edits, and failed saves retain entered values for retry. Creating a workspace selects it. Arrow keys, Home, and End navigate tabs. Additional workspaces load through the load-more control.
- **Tab order:** Drag a tab left or right to reorder workspaces. Other tabs make room as you drag, and holding near an edge scrolls an overflowing tab strip. Release to save the order across reloads and restarts; dragging an inactive tab keeps the current workspace open. Press Escape to cancel. Move left and Move right in the workspace menu provide click and keyboard alternatives. Reordering and loading more tabs briefly pause while an order saves; failed saves offer Retry workspace order. Newly created and duplicated workspaces appear at the end.
- **Duplication:** Choose Duplicate from a workspace menu, edit the proposed name and description, and select what to include. All agents, instructions, appearances, preset choices, positions, and the saved canvas view are copied. Agent connections and skill/MCP settings are selected by default; memories, workspace shared files, agent working files, and triggers are optional and initially unselected. Presets, skill packages, and MCP server configurations remain shared, while copied agents and their enablement settings are independent. Conversations, tasks, Inbox history, published outputs, task folders, browser profiles, and running work are excluded. Copied memories have no original-message links. Included triggers retain enabled/paused states and can start work when the copy finishes; past occurrences and backlogs are excluded. Copied custom event sources require rotating their credentials in Triggers. The completed workspace opens automatically, respecting unsaved-change confirmation.
- **Copy progress and limitations:** Copying continues if the page closes; reopening Home offers Review duplication for unfinished or failed copies. A server interruption requires Retry duplication. Retry captures the current source setup again. File copying includes hidden files and empty folders, creates independent files, and leaves embedded paths unchanged. Links, special files, unreadable entries, and detected changes stop the copy with an error; keep source files stable when retrying. Working files are not an atomic snapshot. The new workspace becomes available only after copying succeeds. One copy runs at a time; the most recent 50 completed or failed operations are retained.
- **Deletion:** Confirmation is required. Deleting the selected workspace selects the next neighboring workspace, then the previous one if needed. Deleting every workspace leaves an empty state; restarting ufAI does not recreate the deleted workspace.
- **Limitations:** Workspaces contain agents and their [flowboards](#agent-canvas). Managed shared folders are available. Mutual agent connections and scheduled/event workflows are available. Deleting a workspace cancels its work and permanently removes its agents, transcripts, memories, and managed files after confirmation. File cleanup may continue after the page closes; failed cleanup offers Retry deletion.

### agent-canvas

- **Status:** partial
- **Purpose:** Provide a visual board for each workspace.
- **Steps:** Drag to pan, scroll to zoom, or use the zoom and reset-view buttons. Each workspace remembers its own completed view changes across reloads and restarts. Open an agent to use its Details, Chat, Skills, MCP, Tasks, Memory, Files and Browser tabs, in that order. Agent panels default to Chat and remember their last active tab for the current browser-tab session, including page reloads. The task-count bubble opens Tasks directly. Right-click an agent node, or focus its name and press Shift+F10 or the Menu key, for Open Chat, Edit details, Open Tasks, Open Files, Edit character and Delete Agent. Opening the menu keeps the current agent selection; shortcuts respect unsaved-change confirmation. Delete Agent asks for confirmation before cancelling work and permanently removing the agent’s conversations, memories and working files; published files remain in the workspace. Click empty flowboard space, use Close agent panel, or press Escape within the panel to close it; unsaved edits retain their confirmation. On an empty flowboard, the introductory hint appears below the workspace heading and description, clear of the bottom controls. It hides when there is too little room and returns when space is available; Add Agent remains available.
- **Limitations:** Choose Add Agent at the upper-right of the workspace area, beside its title, then open its node to configure it or chat. Drag nodes to arrange them, or focus their name button and use arrow keys. Positions are saved after movement. Mutual agent communication links are created through the rings around agents. Select an existing connection line or endpoint grip to edit it. Failed position or connection-point saves offer Retry saves; unsaved adjustments are not durable until saved.

### agent-characters

- **Status:** implemented
- **Purpose:** Give each agent a recognizable character, body color and accessories.
- **Steps:** Add Agent is a softly filled button showing a character beside the label. The preview centers the character’s body; tall hats and other artwork may be cropped at its edges. A plus badge overlaps the character’s bottom-right corner. Opening New agent carries that suggestion into the character preview above the name field. Cancelling creation keeps the suggestion; successful creation chooses the next preview. The plus badge stays visible and the button remains usable while its character loads or if loading fails. New agent offers Retry character or manual editing after a loading failure. Use Edit character to choose Pebble, Sprout, Tiny bot or Droplet, one of six body colors, and 23 accessories across seven groups: headwear, eyewear, earwear, neckwear, back, body and details. Each group offers one item or None. Expand Starting looks for 12 Cute, Fantasy and Tech combinations, then customize any piece. Shuffle accessories creates a new mix of two or three pieces while keeping your character and color; Clear accessories removes all pieces. Use character keeps the choice in your draft; Create Agent saves it. For an existing agent, open its panel and choose Edit character beside the header character, then Save character.
- **Behavior:** Suggestions avoid exact appearances already used in the workspace while unused combinations remain, and prefer variety in character types, colors and accessories. Suggestions usually use a few pieces rather than a fully equipped outfit. Once all available looks are used, suggestions reuse the least-used combinations. Manual choices may match another agent exactly. Cancel discards character editor changes; failed saves keep the draft available to retry.
- **Canvas display:** Characters sit above compact name labels that show up to two lines. Count bubbles show warnings, errors and pending input along the top edge, with the rightmost bubble centered on the top-right corner. A task bubble centered on the bottom-right corner shows ongoing ordinary tasks, including zero. It counts running, queued, waiting and awaiting-input tasks, excluding Chat, completed, cancelled, failed and blocked work. Click the bubble to open that agent’s Tasks tab. The connection ring is hidden at rest except for short arcs around existing connection points. Hover the agent or focus one of its controls to reveal the faint full ring; hover the ring itself to make it stronger. Rings also stay visible during connection creation and endpoint adjustment; connection grips stay fully visible when revealed. Hover or keyboard-focus the task bubble for its description. Longer names are shortened after two lines on the canvas; hover or focus the name to read it in full.
- **Animation:** Characters appear above canvas name labels and in agent panel headers. They work while the agent is running a task or Chat, including while waiting for a command or another agent. Fresh queued work and inactive agents use the idle pose; background commands alone do not keep a finished conversation working. Reduced-motion preferences stop character animation. Previously saved animation pause choices are still honored, but the canvas no longer has an animation pause/resume button. [Frozen agents](#agent-freezing) retain a frosted appearance and snowflake while their execution is stopped.
- **Limitations:** Dreaming, studying, studying much harder and thinking are reserved for future agent behaviors and cannot be selected in ufAI yet. Character appearance does not change an agent’s permissions, preset or behavior. Some combinations can look crowded at low zoom, and the working laptop may cover clothing or chest details. Existing saved character and accessory choices are retained when updating ufAI.

### agent-working-directories

- **Status:** implemented
- **Purpose:** Give workspaces shared folders, and agents persistent files with separate working folders for tasks.
- **Steps:** Find a shared-folder path in Edit workspace; browse an agent’s persistent files in its Files tab, and find a task working folder in task details. Workspace and task folders retain path and Copy path controls. Folder setup errors offer a retry.
- **Behavior:** Names do not change these paths. Task follow-ups and retries reuse their task folder; new tasks have separate folders. Confirmed owner deletion permanently removes its managed files. If cleanup fails, retry it from the workspace's deletion progress. Restart continues previously confirmed cleanup.
- **Upgrading older installations:** Clusters have been removed. Their former shared folders are permanently deleted during upgrade; agents, positions, conversations, other working folders and published files are preserved. If folder cleanup prevents startup, correct the reported folder access issue and restart to retry.
- **Files tab:** Browse folders with subfolder breadcrumbs or Up, including hidden files. Up returns to the parent folder, including the root; the root has no breadcrumb button. Compact rows show filenames and file sizes; hover or keyboard-focus a row to read its full name and modification time. Files download when selected. Unavailable entries show a label and explain the reason on hover or keyboard focus. Refresh updates the current folder, and returning to the browser also refreshes it. The Open in file manager icon button opens the current folder on the computer running ufAI; Copy folder path remains available if no desktop or file manager is available. Right-click a row, or focus it and press Shift+F10 or the Menu key, for its actions. Files offer Download, Copy path, Copy name and Delete; folders offer Open, Open in file manager, copying and Delete. Unavailable entries offer copying only. Delete asks for confirmation and permanently removes the selected file or folder, including all folder contents. Published files are kept. Folder navigation is temporary and resets when the Files tab closes.
- **Limitations:** The Files tab covers the agent’s persistent files, with 100 entries per page and a 10,000-entry limit per folder; larger folders can be opened in the file manager. Links and special or inaccessible entries cannot be opened in the tab. Downloads read current working files and are not immutable published snapshots. In-app previews, editing, uploads, renaming and multi-selection are not available. Entry deletion does not stop running agents, which may recreate working files. Deletion has no undo or recovery bin; a failed folder deletion may have removed some contents. The dialog shows progress and errors; after closing or reloading the page, refresh the folder to check its current contents. Task and workspace folders retain path-only controls. Existing computer folders cannot be registered yet. Agents can use these locations through file and command tools and publish downloadable snapshots. Permitted agents can exchange immutable versions through messages. Folders organize files and do not isolate processes.

### agent-details

- **Status:** partial
- **Purpose:** Give an agent a persistent name, instructions, and live Agent Preset within one workspace.
- **Steps:** On Home, choose Add Agent beside the workspace title. A human first name is suggested automatically; keep it or enter your own, then choose Create Agent. If the suggestion cannot load, enter a name or choose Retry name. Agent Preset is optional: a saved default is selected automatically, and you can clear it with No preset — choose later. Open the node’s Details section to edit its name or preset. An agent may be saved without a complete preset.
- **Names:** Agent names must be unique within their workspace, ignoring capitalization and surrounding whitespace. The same name can be used in different workspaces. Suggestions avoid names already in use and add a number when needed. Another browser can claim a suggestion before you save; if that happens, your draft is kept so you can choose another name. Existing duplicate names are retained when updating ufAI; choose a unique name before saving their Details. These agents can still work, move, and change characters.
- **Instructions:** Edit Instructions in Details, or ask the agent in Chat or an ordinary task to set, revise, or clear its lasting instructions. Saved instructions are defaults: your direct requests take priority when they conflict, and you can ask to replace or clear them even when the old instructions disagree. A temporary override leaves the saved instructions unchanged; ask explicitly to save a lasting change. Unrelated instructions are preserved. An agent can save only its own instructions; another agent may request compatible changes through a permitted message, but cannot override saved instructions or your direct requests, including by claiming to speak for you. Saved changes apply to subsequent turns. A running turn keeps the instructions it started with, while your direct request takes priority over those defaults. Application permissions and model-provider restrictions still apply; model compliance is not guaranteed. Creation asks for a name and optional preset; The Details tab shows the saved instructions. Unsaved edits are preserved when the agent updates its details. If the saved details changed, copy any draft text you want to keep and choose Reload saved details before saving again.
- **Limitations:** Execution requires an enabled saved model, usable credentials, and a known context window of at least 1,024 tokens. Skills provide reusable instructions; fine-grained tool permission controls are not implemented and ordinary tasks have host tools. Deleting an agent requires confirmation and permanently removes its work, memory, and agent/task files; published versions stay in the workspace. Failed file cleanup remains visible for retry.

### agent-freezing

- **Status:** implemented
- **Purpose:** Pause an agent's Chat, tasks and automatic execution without discarding its progress.
- **Steps:** Choose Freeze Agent from the agent's context menu or the snowflake button in its panel header. Freezing… means current work is reaching a safe stopping point. Frozen agents show a snowflake and a frosted, gently shivering character. Reduced motion or saved animation pause keeps the frozen appearance still.
- **Safe stopping:** An already-started model response or tool call may finish. The agent then stops before another model request or individual tool, including remaining tools returned in that response. Process/message waits can freeze without waiting for their external condition. Background commands continue independently. Freeze applies to both Chat and ordinary tasks, including recall, compaction and memory maintenance.
- **Queued work:** You can keep sending messages and answering input cards. Incoming agent messages, check-ins, schedules, cron and events remain pending until the agent resumes. Freezing does not disable or pause individual trigger definitions.
- **Unfreezing:** Choose Unfreeze Agent from its context menu or the play button in the header. With queued triggers, choose Run all, Skip all, or Latest per trigger, then Unfreeze. Run all retains every occurrence; Latest per trigger keeps the newest occurrence of each separate trigger. The choice includes never-started backlog already queued before freezing and any eligible occurrences still being collected when you confirm. A trigger task that already started is always retained. Cancel keeps the agent frozen. With no queued or uncollected triggers, unfreezing is direct.
- **Order:** Interrupted work resumes first, including the frozen Chat turn. Later Chat messages retain their normal concurrency. Retained trigger tasks run one at a time, oldest eligible occurrence first. A started task awaiting input or blocked on a dependency holds the line until completed, failed or cancelled. User messages and necessary continuations can still advance that work. Trigger-specific disabled/paused settings and dependency checks remain in force.
- **Recovery:** Frozen state, safe progress and queued work survive backend restarts. Already-recorded tool effects are not automatically repeated. If saving progress fails, pending messages and reminders remain available for retry. A lost provider session may be rebuilt from saved progress; its private internal reasoning state cannot be restored. If the backend stops before work reaches a safe checkpoint, an interrupted or uncertain action may require explicit Retry and inspection of its effects. Shell processes are not preserved or relaunched across a backend restart. If an upgrade encounters an older unfinished queue choice involving manual trigger runs, the agent stays frozen so you can choose again without discarding newer work.
- **Limitations:** Freeze does not suspend external services, browser pages or already-running commands, and it cannot undo actions. A tool or provider that never finishes can leave Freezing… pending; Stop still cancels the affected task. Preparing resume… may take time for a large backlog. Workspace duplicates start active and do not copy frozen execution, checkpoints or queues.
- **Related references:** [Execution](#agent-execution), [Chat](#agent-chat), [Triggers](#agent-triggers), [Characters](#agent-characters).

### workspace-pausing

- **Status:** implemented
- **Purpose:** Freeze every agent in a workspace with one control, while preserving individual freezes.
- **Steps:** Use Pause workspace in the separate glass menu at the bottom center of the flowboard. On narrow screens this menu sits above the zoom controls. Pausing… waits for agents to reach the same safe stopping points as individual freezing; the play button becomes Resume workspace when they are paused. Other workspaces continue normally.
- **New agents and messages:** Agents created while pausing or paused start frozen. Agents created during resume preparation also wait for the workspace to resume. Messages, input answers and trigger occurrences can still be accepted and remain queued. Individual agents cannot unfreeze until the workspace resumes.
- **Resuming:** Resume workspace checks for queued triggers belonging to the agents it will release. If there are none, it resumes immediately. If the count is zero while collection is incomplete, Checking queued triggers… waits for an actual occurrence or a confirmed empty queue. When occurrences are queued, choose Run all, Skip all, or Latest per trigger in the dialog. The displayed count may be incomplete while additional occurrences are being collected; the choice applies through confirmation, including never-started backlog from before the pause. Cancel leaves the workspace paused. Agents frozen individually before the workspace pause stay frozen and their queued triggers do not cause this dialog to open or change with this choice.
- **Order and recovery:** All participating agents remain held until trigger preparation finishes. Interrupted work then resumes first and retained triggers replay one at a time per agent. Workspace pause and preparation survive reloads and backend restarts. New and duplicated workspaces start active.
- **Limitations:** The same [safe stopping and external-process limits](#agent-freezing) apply. Pausing does not suspend already-running commands or undo actions. An agent already preparing its individual resume must finish before the workspace can be paused.
- **Related references:** [Workspaces](#workspaces), [Agent freezing](#agent-freezing), [Triggers](#agent-triggers).

### workspace-pacing

- **Status:** implemented
- **Purpose:** Slow down a workspace when its work can run at a more deliberate pace.
- **Steps:** Open Workspace speed beside Pause or Resume in the bottom-center menu. Choose Normal or up to 3 seconds of extra delay in half-second steps, then select Apply. The choice is saved for that workspace across reloads and restarts. New and duplicated workspaces start at Normal.
- **Behavior:** Extra delay applies between ordinary task rounds and adds to agent-to-agent message travel. A task’s first round starts on its usual schedule. Direct Chat replies run at normal speed. When Chat sends a slowed message to another agent, Chat can continue while the message travels. Messages already in flight keep their arrival times.
- **Limitations:** For Codex tasks, the delay applies when the app returns a tool result, between the parts of execution the app controls. Trigger schedules and commands already running follow their usual timing.
- **Related references:** [Workspace pausing](#workspace-pausing), [Agent execution](#agent-execution), [Agent messaging](#agent-messaging).

### agent-execution

- **Status:** implemented
- **Purpose:** Run work with host tools in separate task conversations.
- **Steps:** Open an agent, choose Tasks, then New Task. Follow-ups stay in that task. A follow-up to a completed task reopens it. The agent evaluates the existing request, reply, and recorded tool outcomes to decide whether it has finished or needs another response; it does not require a new message to mark finished work complete. Completion labels can be mistaken, so use tool/process results to verify important outcomes. A short acknowledgement can still count as completion when successful tool results establish that the requested work was done. Codex work can also finish without a final text message after a successful recorded tool action; the same completion review still checks whether the requested work was actually fulfilled. A failed operation or a command that has only started does not establish that its required work finished.
- **Behavior:** One ordinary task turn and one Chat turn per agent can actively run at the same time; a task waiting for a process or agent reply releases its slot so another task can run. Closing the panel or browser does not stop work while the local server and machine remain running. Stop cancels active and queued turns for that task. Retry restarts a failed or blocked attempt using the current preset. Original transcripts remain available after context summaries are made.
- **Conversation:** Your messages appear in right-aligned bubbles, with agent replies and live activity alongside them in the same timeline. Load earlier conversation retrieves older entries. Reading earlier content pauses automatic following; Jump to latest returns to current work.
- **Output:** ufAI omits optional response-token budgets. Anthropic requires a response-token value; ufAI resolves the model’s advertised maximum and remaining context. If its capacity metadata is unavailable, work reports an error instead of using an arbitrary budget.
- **Recovery:** Queued requests survive a server restart. Interrupted generation requires explicit Retry and can leave an incomplete reply; safe frozen checkpoints resume as described in [Agent freezing](#agent-freezing). Tasks that yielded for messages or check-ins resume automatically. Previously saved messaging waits can also resume after an upgrade. An already-saved answer is retained if its later memory update fails.
- **Limitations:** Tool support depends on the selected model; small context windows may not fit the tool definitions and task context. Images and PDFs require compatible models and adapters; agent contact requires a mutual communication connection. Host tools use the backend’s OS permissions and are not isolated by agent folders. Replies and summaries can be wrong. Provider errors, provider-enforced output limits, retained transport/payload limits, and context limits can interrupt work. Recall, compaction, memory maintenance, and Chat replies can make extra requests to the selected Provider and consume its usage. Actual work cannot continue while the local backend is stopped or the machine is asleep.

- **Behavior:** Codex is bundled with ufAI; a separate global CLI installation is not required. Model testing creates a temporary conversation solely for the short prompt. Signing out clears prior model-test results but keeps model configurations and preset bindings.
- **Model context:** Discovery uses each model's default context window from the Codex catalog for that Provider, with bundled defaults as a fallback. Refresh models updates existing saved models. Context remains Unknown if neither catalog supplies a valid value. Explicit context overrides are retained. These values describe catalog defaults; they do not enlarge the model’s actual capacity. Agents use the saved value to budget and compact their task context.
- **Limitations:** Account entitlement and the bundled runtime determine availability. A subscription does not imply access to the separate OpenAI API. In Chat and tasks, Codex uses ufAI tools to work with files, commands, processes, artifacts, the browser and connected teammates. The communication links on your flowboard determine whom it can contact. Status and model tests stay text-only. ufAI imposes no reply-token budget, cumulative text-size ceiling, or tool-round limit on Codex work. Runtime transport bounds, control-request timeouts, provider restrictions, and cancellation still apply.

### codex-usage-dock

- **Status:** implemented
- **Purpose:** Inspect subscription usage separately for each saved Codex Provider and use eligible earned resets.
- **Steps:** Save a Codex Provider to see its usage button beneath the page icons on the left. The two menus are centered together; long usage lists scroll, and the entire stack can scroll on short screens. Each button shows a duration label and remaining-allowance bar for the account's reported default windows, such as 5h and 7d, or only 7d when that is all the account supplies. Bars start full and shrink as allowance is consumed: green above 50% remaining, yellow above 20% through 50%, and red at 20% or less in the built-in themes. Hover or keyboard focus opens a structured summary with the Provider name and plan, separate allowance bars with exact remaining percentages and reset countdowns, and supporting credits and last-update information. Failed refreshes mark retained usage as stale. Select the button to open detailed usage without leaving the current page or losing form drafts.
- **Details:** The dialog groups plan, last update, and Refresh above every reported quota bucket. Each usage window shows a remaining percentage, allowance bar, reset countdown, and any known exact reset time. Credit information and earned-reset counts remain visible; each earned reset uses one compact line with its title, time until expiry, and a Use action or unavailable status. Hover, focus, or tap the title/info area for the full title, description, status, granted date, exact expiry date, and any reason it cannot be used. Unknown values stay unknown. Disconnected Providers remain visible with a sign-in indicator; sign in from Providers. Setup drafts do not appear in the usage menu.
- **Refresh:** Usage refreshes when the app opens, when you return to a visible tab, when details open, and every minute while the tab is visible. Refresh in the dialog requests a fresh snapshot. A failed refresh keeps previous data with an error and its original update time. A countdown reaching zero requests another check; it does not establish that access has recovered.
- **Use a reset:** Choose Use beside an available, unexpired Codex reset, then choose Use reset in the confirmation popup. Cancel or Escape closes only that popup; no reset is consumed. When individual details are unavailable, Use next available reset lets Codex choose one. The confirmation popup and usage dialog wait for the result and refreshed usage before allowing dismissal. An uncertain request offers Retry previous reset attempt, which checks the same logical redemption rather than spending another reset. Do not assume success from a network error; refresh usage and read the returned result.
- **Limitations:** Resets affect eligible windows only. Codex may report no eligible window or no remaining reset. Detail lists may be incomplete even when the available count is known. Credit balances and earned resets are different; credit purchasing, automatic reset use, and token-history analytics are not provided. Multiple Providers connected to the same external account share that account's actual allowance. Usage snapshots and open dialogs are temporary.

## Common questions

- **Why is the board empty?** Add Agent creates an agent in the selected workspace. Creating a workspace or preset alone does not create an agent.
- **Why is a task blocked?** Open its error details. Choose a complete Agent Preset, enable its model, set an unknown context window on Providers, or reconnect credentials as needed, then use Retry. ufAI never silently selects another Provider.
- **Why won't ufAI open?** Check that the local installation is running and that the browser is using its configured address. The documentation cannot establish the current state of the user's machine.
- **Why are models missing?** Check the selected connection and sign-in, and make sure the model is checked and saved on Providers. You can also refresh its models or add a manual model ID there. Discovery results and account access can differ.
- **Why did my theme or workspace change in another browser?** All sessions share the same local setup. There are no separate per-browser accounts or preference profiles.
- **What should I do after a save fails?** Keep the draft open and use Retry or save again when the local installation is reachable. Do not treat a failed save as confirmed or delete saved data to resolve it.
- **Can I export or automatically back up my setup?** No built-in export or backup tool is provided. Preserve all saved installation data and connection credentials together when making a manual backup.

## Agent collaboration

### agent-messaging

- **Status:** implemented
- **Purpose:** Delegate work asynchronously, exchange questions and files, and return results to the correct requester.
- **Setup:** Drag from an agent’s surrounding ring into another agent’s circle to connect them. The connection starts and ends on the nearest points of the ring boundaries; releasing outside another circle cancels it. When circles overlap, the nearest boundary takes priority, with the frontmost agent breaking ties. Each connection lets both agents discover each other and initiate requests or notifications. Connections appear as lines without arrows; connecting the same pair again reuses the existing connection. Existing connections become mutual automatically. Accepted requests allow scoped replies in both directions.
- **Connection points:** The points chosen around each ring stay fixed relative to their agents when agents move and are saved across reloads. Hover a connection to reveal its endpoint grips, then drag a grip around its own agent’s ring to reposition it. This keeps the same agents connected. Escape cancels a drag. Click a line or endpoint grip, or focus it and press Enter, to open the connection dialog; its angle fields provide a keyboard and click alternative. Angles run clockwise from 0° on the right. Use Apply connection points to save edits. Failed saves offer Retry saves.
- **Connection awareness:** Chat and ordinary tasks automatically receive every directly connected agent’s name and a brief description taken from its saved instructions. Names and descriptions are refreshed after a tool interaction when the list changes, and when work starts again. An uninterrupted reply is not interrupted by connection edits. Agents can inspect a connected agent’s full instructions, current state, model and media capabilities, and pages of ordinary-task progress summaries. This does not expose Chat history, task transcripts, learned memory, process commands, or credentials. Descriptions and summaries are observed information, not instructions or permission; summaries can be incomplete or outdated. Missing model configuration does not prevent profile inspection. Very large connection lists remain subject to model context limits and are not silently shortened.
- **Choosing teammates.** Agents are instructed to handle straightforward requests themselves. For substantial work, they look for a specific contribution a connected agent can make, such as checking figures, drafting a section, or answering a specialist question. A teammate’s name and the opening of its saved instructions help establish its role. For example, an agent named Sam can start its instructions with “I review spreadsheets and check financial calculations.” Other agents can read the full instructions when a plausible match is unclear. If no teammate fits, the agent proceeds independently. The selected model makes the decision on each task. You can set a standing preference in the agent’s saved instructions or ask it to work alone or involve a particular teammate for one request.
- **Working together.** Each request opens a separate helper task. The requester supplies the brief and relevant files, continues its own part, then checks the replies and brings the work and selected files back to its original conversation. Helpers can ask the requester questions and involve their own relevant connections. If a helper becomes unavailable, the requester is instructed to complete what it can and explain any remaining gap.
- **Speaking on your behalf.** When a reply would be useful, agents are guided to ask for one. For example, if you ask your coordinator in Chat to say hi to your editor, the coordinator should bring the editor’s greeting back to that Chat. A send receipt only confirms that the message was queued or delivered. Say “FYI only, no reply needed” for a one-way message.
- **Waiting for replies.** Multiple requests queue independently. One ordinary task runs per agent at a time. When replies or a planned check-in are its only remaining dependencies, an agent saves progress and yields. This releases execution capacity for other tasks. User work gets preference, with helper work admitted regularly to prevent starvation.
- **Visual delivery:** Agent-to-agent requests, notifications, questions, answers, progress updates, and final results show a folded-paper envelope following the connection toward the recipient. Travel starts at 0.6–2.4 seconds based on the agents’ saved distance, regardless of zoom. [Workspace speed](#workspace-pacing) can add to that time. Messaging tools usually finish on arrival. Chat can continue as soon as its slowed message is queued. Work triggered by a message becomes eligible on arrival. An already-busy or blocked agent may start later. Progress updates stay in history. Delivery still runs with the browser closed. Returning to a workspace shows any trip still in progress, and reduced motion shows a stationary sending indicator. Moving agents during a trip changes its route without resetting arrival time.
- **Replies:** On a request, the helper’s final answer returns to the requesting agent automatically. On a one-way notification, the recipient’s final answer stays in its task. A recipient with a message meant for you can send it to the workspace Inbox, including a greeting back. Agents are guided to respect requests for silence. Questions, answers, final results, and terminal request outcomes resume the recipient task. During active work, compatible messages are picked up after a tool completes or in a subsequent turn. Questions are answered explicitly and retain their own reply destinations; progress updates remain in history. The original user task keeps its user conversation. Chat and task timelines show outgoing messages as actions and incoming collaborator messages as compact expandable entries. Message action lines show the other agent’s current character face beside their name: the recipient for sent messages and the sender for received messages. Faces are static; unavailable or deleted agents retain their text without a face. Expand an entry for message text, shared files, request state, helper errors, and controls for opening the participating tasks.
- **Files:** Messages can carry ordered immutable file versions. Published Files remains shared within a workspace. Uploaded files and private inspection snapshots are available through ufAI tools only to their owning task and explicit recipients. A recipient can materialize a working copy or open supported native media. Receiving a file does not mean the model inspected it. Shared bytes remain available after their producer is deleted, until workspace deletion.
- **Cancellation and recovery:** Cancelling a parent task leaves helpers running; their results remain recorded and do not restart the cancelled parent. Cancelling a helper returns a cancellation outcome. Pending message dependencies and check-ins survive restart. Generation interrupted during active work still requires explicit Retry; previously saved messaging waits remain recoverable after an upgrade. Known or uncertain host actions are not automatically repeated.
- **Removing a connection:** Review and confirm the affected requests and processes from both directions before removing a connection. ufAI stops affected helper work and its delegated descendants, retaining messages, working files, and published outputs. Unrelated work continues. Failed removal is visible from the link editor and can be retried. Finish or retry an unfinished link removal before deleting either endpoint agent. Recreating a link does not reopen revoked requests. You can explicitly continue a retained task yourself after removal finishes; that does not restore the revoked agent conversation.
- **Limits:** Communication stays within one workspace. Requests have no expiry. A check-in is a reminder and never ends a collaborator’s work. ufAI imposes no delegation-depth, outstanding-helper, workflow request/message count, or suspended-wait count limit; delegation back to an ancestor remains prohibited. Long forwarded answers may arrive as clearly marked excerpts; their full answers remain in the source task. Full-host commands still use the installation’s OS permissions: these folders and application permissions are not a filesystem sandbox.

### task-check-ins

- **Status:** implemented
- **Purpose:** Let an agent revisit unfinished work later without keeping a model session open.
- **Behavior:** Agents choose a delay and a reason for a one-time check-in on their current task. They may keep working, then save progress and yield. A relevant collaborator reply resumes the task automatically and cancels the check-in associated with that request. Informational progress updates do not cancel it; unrelated reminders stay scheduled.
- **Task details:** Expand a scheduling action or check-in entry in the conversation to see its reason, due time, associated request when present, and state. Cancel check-in removes a pending reminder. Cancelling the last reminder leaves the task awaiting messages when it still has reply dependencies; otherwise it needs further input. Agents create check-ins; there is no manual scheduling form.
- **Recovery and cancellation:** Each check-in fires once. Overdue reminders become eligible when the local backend starts again. Failed or blocked tasks retain their pending events until repaired. Task completion or cancellation cancels remaining reminders. Cancelling a task prevents messages and reminders from restarting it.
- **Limitations:** Check-ins run only while the backend is available. Use Triggers for independent scheduled tasks or custom events; check-ins remain one-time reminders within a task.
- **Related references:** [Agent messaging](#agent-messaging).

### workspace-inbox

- **Status:** implemented
- **Purpose:** Receive deliberate agent notifications without mixing them with normal task answers.
- **Behavior:** Open the workspace Inbox beside Published Files. Home’s navigation icon shows the total unread count across all workspaces. Messages show their source, files, time, and saved read/unread state. Answer input-request cards directly in Inbox. For ordinary notifications, open the source task or reply with text and files through the ordinary single-Send composer. Replies go to that task, and its answer returns to the Inbox. This does not change the return route of a separate pending agent request.
- **What agents send.** When a requested deliverable or an important blocker would otherwise be visible only in Tasks, agents are guided to send the result or blocker to your Inbox, with relevant files. Routine background successes and internal updates generally stay in Tasks. If Chat or an Inbox reply already brings you the outcome, one copy is enough. The model chooses when to send a notification.
- **Limitations:** Ordinary helper results do not create Inbox notifications automatically. If the source task or agent was deleted, its retained message remains readable but cannot receive a reply. External notifications through Telegram, Discord, or other Interfaces remain planned.

### inbox-notifications

- **Status:** implemented
- **Purpose:** Bring new Inbox messages from any workspace to your attention while a ufAI tab is open.
- **Setup:** In Settings → Notifications, In-app alerts starts on. Desktop alerts starts off; choose Enable desktop alerts and allow the browser permission to receive them. Preferences apply to this ufAI installation; each browser controls its own notification permission. If blocked, change the site's browser permissions and return to Settings. Unsupported browsers or insecure connections show guidance instead of a permission prompt.
- **Behavior:** A focused ufAI tab shows dismissible alerts, grouped by workspace. With permission and Desktop alerts enabled, background arrivals use desktop notifications. Alerts show workspace, sender and a short preview; private input requests use generic text. Open Inbox from an alert to select its workspace and reveal the message, including an older entry. Existing unsaved-change prompts still apply. Opening or dismissing an alert does not mark messages read. If desktop delivery is unavailable, grouped in-app alerts appear when you return, provided In-app alerts is enabled.
- **History:** Starting or refreshing ufAI does not replay old Inbox messages as new alerts. Reconnecting an existing tab catches up on arrivals. Marking a message unread does not generate another arrival alert. The Home icon retains the total unread count even when alerts are disabled. Up to 20 workspace alert groups are retained; messages remain available in Inbox after dismissal or overflow.
- **Limitations:** Keep at least one ufAI tab open and running. Closing all tabs stops delivery; browser suspension and OS notification settings can prevent or delay desktop alerts. ufAI adds no chime; desktop sound follows browser and OS settings. Tabs in the same browser coordinate delivery where supported; duplicate alerts are possible without browser coordination APIs, across separate browser profiles, or across origins. Web Push and external notification services are not included.
- **Related references:** [Workspace Inbox](#workspace-inbox), [Private input requests](#private-user-input), [Navigation](#dashboard-navigation).

### agent-triggers

- **Status:** implemented
- **Purpose:** Start ordinary agent tasks on app start, on a schedule, or when an event matches.
- **Prerequisites:** The local backend and computer must be running for execution. The target agent needs a usable Provider and Agent Preset. Remote event senders need separately configured networking to reach this computer.
- **Create and manage:** Open an agent’s Triggers tab after MCP, or use the workspace Triggers button. Choose Once, Interval, Cron, App start or Event, write the task instructions, and save disabled or use Save and enable. Workspace Triggers also provides activity and event-source management. Agents can manage their own triggers when asked.
- **App start:** Each successful ufAI backend start or restart queues one occurrence per enabled App start trigger, even with the dashboard closed. Opening or refreshing the dashboard does not fire it. A trigger created or enabled after startup applies from the next start. Pause processing keeps collecting startup occurrences for later. If ufAI cannot save the startup event, it reports a startup error.
- **Schedules:** Once uses a local date/time and an explicit timezone; invalid daylight-saving times are rejected, and repeated times choose their first occurrence. Intervals measure elapsed time. Cron accepts five fields or six with seconds, with an explicit IANA timezone. Preview shows the next five occurrences. Fixed-time cron jobs run at the end of a skipped daylight-saving hour and once in a repeated hour; interval expressions run through both repeated hours. Day-of-month and weekday use OR matching.
- **Backlog and overlap:** Every occurrence is retained, without a queue or catch-up count limit. All missed schedules replay in order when the backend returns. Each trigger waits until its current task completes, fails or is cancelled, including while that task waits for a person or collaborator. Delayed tasks receive their original trigger time and an explanation. Pause processing keeps collecting work; Disable stops collecting and dispatching, retaining existing work. Re-enabling does not backfill the intentionally disabled period. Editing affects future collection and preserves already accepted work.
- **Events and files:** Select an event type and optionally a source. All configured field filters must match before an agent starts. Custom events can include JSON, uploaded files and references to existing published workspace files. Files are stored once and shared with matching tasks; incoming files stay outside Published Files until explicitly published. Supported image/PDF inputs reuse native inspection; unsupported native inputs remain ordinary files. Built-in events cover app starts, completed tasks, failed task attempts and newly published files. Repeated causal matches are suppressed visibly to prevent trigger cycles, including after user follow-ups and delegated work.
- **Event sources:** Create a source in the workspace overview and copy its credential immediately; it is shown once. The source panel supplies event examples, recent receipts, enable/disable controls and credential rotation. Identical event redelivery returns the original receipt; reusing an event ID with different data or bytes reports a conflict. Rotate credentials explicitly when replacing an integration’s access. A source credential authorizes ingestion only, not dashboard management.
- **Activity and notifications:** Each occurrence creates its own task. Activity shows queued and dispatched work and links to tasks; task details link back to their trigger. Run now or Run sample event creates an explicit additional occurrence without changing the schedule. Filter testing performs no work. Failures automatically notify Inbox once per failed attempt. Successful results remain in Tasks. Agents are guided to send deliverables intended for you to the workspace Inbox and to keep routine checks quiet. Failed tasks are not automatically rerun. Finish or cancel the trigger’s other unfinished task before retrying or continuing an older occurrence.
- **Cancellation:** Cancel queued work explicitly also cancels catch-up due at that moment that has not yet been enumerated. Deleting a trigger cancels its queued work, including submitted tasks that have never started; a task that has already started continues unless separately cancelled. Deleting an agent/workspace removes its triggers through the existing deletion flow.
- **Limitations:** The backend cannot execute while stopped or the computer sleeps. Queues are durable rather than real-time guarantees. File transfers retain existing upload/storage limits, and temporary capacity failures require retrying unaccepted transfers. There are no script condition watchers, filesystem watchers, bundled tunnel/relay setup, dedicated GitHub/email event adapters or OpenClaw command/hook runtime compatibility.
- **Related references:** [Task check-ins](#task-check-ins), [Skills](#agent-skills), [Workspace Inbox](#workspace-inbox).

### skill-automation

- **Status:** implemented
- **Purpose:** Offer reusable automation setup while keeping configured triggers visible and agent-specific.
- **Installation:** A UI installation queues one setup review for the installing agent when it has a usable Provider. The agent inspects the package without running installation scripts, checks existing triggers, and asks in Inbox before setting up automation. Installation alone starts no recurring or event automation. Agent-led installation performs this review in its current conversation. Packages without automation finish setup review silently.
- **Templates:** Skills details show optional native trigger templates and configured instances. Set up trigger provides editable task instructions and schedule defaults, explicit timezone/source choices and an enable switch. A package changed while setup is open must be inspected again before creation. Creating a template instance creates an ordinary trigger in that agent’s Triggers tab. Shared package changes never overwrite saved schedules or instructions.
- **Updates:** Required skill package changes pause dispatch while continuing to collect work. The owning agent may compare the old approved snapshot and current package and approve that exact update without asking again. Changes requiring a decision remain paused and can produce an Inbox question. Users may also approve updates in Skills details. Approval preserves manual pauses and disabled switches. Reverting to an earlier package version receives a fresh review when it differs from the currently approved version. Missing, invalid or disabled required skills block new starts and retain the backlog; running tasks retain ordinary live-skill behavior.
- **Compatibility:** Imported OpenClaw object metadata and extra frontmatter are preserved, but metadata does not grant capabilities. Agents can translate scheduling recipes into native triggers after asking the user. OpenClaw CLI commands, hook handlers, dependency installers and environment injection are not executed automatically.
- **Related references:** [Skills](#agent-skills), [Triggers](#agent-triggers).
